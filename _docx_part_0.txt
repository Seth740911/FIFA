BackgroundOur 2026 FIFA World Cup viewing guide website (running on port 8086) uses HLS (HTTP Live Streaming) to play match highlight videos sourced from FIFA's official CDN. To improve user experience, we implemented a client-side video caching system using IndexedDB, so that once a user watches a match video, subsequent visits would play from local cache instead of re-downloading from the network.However, the system never actually worked in practice. Every time a user clicked on a match, the video would stream from FIFA's network, even on repeat visits. On mobile phones, the situation was worse — the background cache download never even started.2. Problem DescriptionThe core symptom: "每次都是抓流播" — Every time the user clicks a match, video streams from the FIFA network. The local IndexedDB cache is never used for playback, even when cache data exists from a previous visit.The expected behavior: First visit streams from network + downloads to IndexedDB in background. Second visit plays from local cache directly, with no network streaming.PlatformExpectedActualPC (Chrome)Stream → Cache → Replay from cacheStream → Cache deleted/incomplete → Stream againMobile (Android)Stream → Cache → Replay from cacheStream → No cache starts → Stream again3. Investigation Process3.1 Initial Code ReviewThe video caching system in index.html (~3200 lines) consists of three main functions:_cacheVideoSegments(m3u8Url, fifaId, viaProxy) — Downloads all .ts segments from m3u8 playlist and stores in IndexedDB_playFromCache(fifaId) — Reads cached segments from IndexedDB and plays them via MSE/HLS.js_playM3u8(url, fifaId) — Main entry point: checks cache first, falls back to network streaming3.2 Diagnostic InfrastructureSince the issue was especially severe on mobile (where DevTools is not available), we built a custom diagnostic system:Backend: Added /api/diag POST endpoint in server.py — writes diagnostic events to .temp/diag.logFrontend: Added _diag(fifaId, event, data) function — uses navigator.sendBeacon() to report key lifecycle events to the backendTracked events: streaming, manifest_loaded, m3u8_fetched, cache_start, cache_complete, cache_failed, bg_cache_failed, play_from_cache, cache_incompleteThis diagnostic system proved invaluable — it revealed that on mobile, the MANIFEST_LOADED event never fired, which was the root cause for Bugs 5 and 6.3.3 Diagnostic Results ComparisonEventPC (Chrome)Mobile (Android)streaming✓✓manifest_loaded✓✗ Never firesmanifest_parsed✓✓cache_start✓✗ Never startscache_complete✓✗bg_cache_failed-status 4034.
