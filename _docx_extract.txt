BackgroundOur 2026 FIFA World Cup viewing guide website (running on port 8086) uses HLS (HTTP Live Streaming) to play match highlight videos sourced from FIFA's official CDN. To improve user experience, we implemented a client-side video caching system using IndexedDB, so that once a user watches a match video, subsequent visits would play from local cache instead of re-downloading from the network.However, the system never actually worked in practice. Every time a user clicked on a match, the video would stream from FIFA's network, even on repeat visits. On mobile phones, the situation was worse — the background cache download never even started.2. Problem DescriptionThe core symptom: "每次都是抓流播" — Every time the user clicks a match, video streams from the FIFA network. The local IndexedDB cache is never used for playback, even when cache data exists from a previous visit.The expected behavior: First visit streams from network + downloads to IndexedDB in background. Second visit plays from local cache directly, with no network streaming.PlatformExpectedActualPC (Chrome)Stream → Cache → Replay from cacheStream → Cache deleted/incomplete → Stream againMobile (Android)Stream → Cache → Replay from cacheStream → No cache starts → Stream again3. Investigation Process3.1 Initial Code ReviewThe video caching system in index.html (~3200 lines) consists of three main functions:_cacheVideoSegments(m3u8Url, fifaId, viaProxy) — Downloads all .ts segments from m3u8 playlist and stores in IndexedDB_playFromCache(fifaId) — Reads cached segments from IndexedDB and plays them via MSE/HLS.js_playM3u8(url, fifaId) — Main entry point: checks cache first, falls back to network streaming3.2 Diagnostic InfrastructureSince the issue was especially severe on mobile (where DevTools is not available), we built a custom diagnostic system:Backend: Added /api/diag POST endpoint in server.py — writes diagnostic events to .temp/diag.logFrontend: Added _diag(fifaId, event, data) function — uses navigator.sendBeacon() to report key lifecycle events to the backendTracked events: streaming, manifest_loaded, m3u8_fetched, cache_start, cache_complete, cache_failed, bg_cache_failed, play_from_cache, cache_incompleteThis diagnostic system proved invaluable — it revealed that on mobile, the MANIFEST_LOADED event never fired, which was the root cause for Bugs 5 and 6.3.3 Diagnostic Results ComparisonEventPC (Chrome)Mobile (Android)streaming✓✓manifest_loaded✓✗ Never firesmanifest_parsed✓✓cache_start✓✗ Never startscache_complete✓✗bg_cache_failed-status 4034. Bugs Found & FixedThrough systematic investigation, we identified 6 bugs. Three were critical for the PC platform, and two were root causes specifically for mobile.Bug 1: _playFromCache deleted incomplete cache [CRITICAL]Location: index.html line ~2217When _playFromCache detected that segBlobs.length < totalSegmentsInPlaylist, it deleted the ENTIRE cached video and fell back to network streaming.This meant even a cache that was 90% complete would be nuked on the next visit.影响: The most destructive bug. Every incomplete cache (which is most caches, since user may navigate away before download finishes) was deleted on next visit, making the cache system effectively useless.修复: Don't delete incomplete cache. If valid segments >= 50%, play from cache with missing segments fetched from a fresh m3u8. If < 50%, fall back to network BUT keep the cache (don't delete it) so it can be completed later.Bug 2: Missing segments used expired signed URLs [HIGH]Location: index.html lines ~2253-2255When _playFromCache played an incomplete cache, missing segments were fetched using URLs from the originally-cached m3u8 playlist.FIFA CDN URLs contain time-sensitive &sig= parameters that expire after a short window.影响: HLS.js tried to fetch segments using expired URLs, resulting in 403/404 errors from FIFA CDN, causing playback failure.修复: Fetch a fresh m3u8 via /api/video endpoint, extract fresh segment URLs from it, and use those for any missing segments instead of expired ones.Bug 3: Synchronous XHR in MANIFEST_LOADED handler [CRITICAL (mobile)]Location: index.html lines ~2459-2461The background cache download was triggered inside the MANIFEST_LOADED event handler using synchronous XHR: xhr.open('GET', m3u8Url, false).Synchronous XHR is deprecated on mobile browsers and silently fails.影响: Background cache download never actually started on mobile browsers, even though the code path appeared correct.修复: Replaced all synchronous XHR with async fetch() chains. This fixed the immediate issue but revealed deeper problems (Bugs 5 & 6).Bug 4: IndexedDB storage quota not handled [MEDIUM]Mobile browsers limit IndexedDB to approximately 50-100MB. A single match video can be 30-50MB.No error handling existed for quota exceeded errors.影响: When storage was full, the cache write silently failed, and no data was stored. No cleanup mechanism existed to free space.修复: Added quota error detection in _saveVideoToDB transaction.onerror handler, plus _evictOldVideoCache() function that automatically deletes the 1-2 oldest cached matches when quota is exceeded.Bug 5: MANIFEST_LOADED event never fires on mobile [CRITICAL (mobile)]Discovery via /api/diag: PC diagnostic log showed streaming → manifest_loaded → cache_start → cache_complete. Mobile showed streaming → nothing.On mobile phones, the connection to FIFA CDN goes through a proxy fallback (viaProxy=true) because direct connection fails due to network restrictions.In this proxy path, the MANIFEST_LOADED event from HLS.js was unreliable or never fired.影响: ROOT CAUSE for mobile. The cache trigger event never fired, so background download never started. Mobile users could never build a local cache.修复: Changed cache trigger from Hls.Events.MANIFEST_LOADED to Hls.Events.MANIFEST_PARSED (which is much more reliable). Extracted all cache logic into an independent _startBackgroundCache() function called from the MANIFEST_PARSED handler.Bug 6: Mobile direct-fetch FIFA CDN returns 403 [CRITICAL (mobile)]Discovery via /api/diag: Mobile diagnostic showed bg_cache_failed: "status 403".FIFA CDN URLs with expired or reused signature tokens reject direct requests from mobile browsers.The _startBackgroundCache() function was attempting to fetch m3u8 and .ts segments directly from FIFA CDN.影响: ROOT CAUSE for mobile. Even after fixing the event trigger (Bug 5), the cache download failed because FIFA CDN rejected the requests with 403.修复: _startBackgroundCache() now fetches m3u8 through the /proxy/ endpoint (server-side proxy) instead of direct fetch. It passes viaProxy: true to _cacheVideoSegments so all .ts segment downloads also go through the proxy. This ensures FIFA CDN sees the request coming from the server's IP, not the mobile browser.5. Syntax Error IncidentAfter fixing Bug 3 (replacing synchronous XHR with async fetch), orphaned try/catch code residues remained in the file at lines 2599-2617. This caused a JavaScript syntax error: "missing ) after argument list", which resulted in a completely blank white screen for all users.The fix was to remove the orphaned code block. This incident highlights the importance of verifying the complete file after refactoring, not just the modified lines.6. Key LessonsMobile is not just a smaller PC: Synchronous XHR, event firing order, and CDN signature handling all behave differently on mobile. Never assume PC testing is sufficient.Diagnostic infrastructure is essential: The /api/diag endpoint was what made it possible to discover Bugs 5 and 6. Without it, we would have been debugging blind on mobile.Don't destroy partial work: Bug 1's approach of deleting incomplete cache was fundamentally wrong. A 90% complete cache is valuable and should be preserved, not discarded.CDN signatures expire: Signed URLs from CDNs are time-limited. Any caching system must handle URL expiration, not assume cached URLs remain valid.Proxy fallback needs end-to-end support: When mobile browsers can't directly access FIFA CDN, the cache system must also use the proxy path. A half-proxy solution (stream via proxy but cache directly) fails.10.
